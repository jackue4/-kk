# 线上包调查：下载慢 & 是否支持多人联机（2026-11-21 晚，只读）

调查对象：https://jackue4.github.io/-kk/ 当前线上包。gh-pages 头版本是 690f4bc（21:07 部署，PvP 锁定描边），三个文件的 md5 和这一版逐个对得上。
它不含测试专项的 BUG 修复（那批没部署）。本次没改代码、配置和存档，没导出、部署或提交，也没碰数值投放会话。

证据都在 `logs/` 下：
- `live_download_timing.txt`：curl 计时、对照测速、压缩估算
- `live_phase_probe.txt`：浏览器分段计时
- `live_pck_list.txt`：线上 pck 文件清单
- `live_gdc_dump_net_main_select_raid.txt`：线上脚本解包

探针脚本在会话临时目录，`live_phase_probe.py` 和 `pck_scan.py` 两个。

## 一、下载为什么慢

### 1. 要下多少（线上实际响应）

| 文件 | 原始大小 | 线上传输（gzip） | 如果改用 brotli-11（本机估算，未改线上） |
|---|---|---|---|
| index.wasm（引擎） | 39,514,754 | 10,248,949（25.9%） | 6,902,599（17.5%） |
| index.pck（游戏资源） | 21,216,760 | 20,877,799（98.4%） | 20,506,044（96.7%） |
| index.js / index.html | 279,815 / 6,591 | 69,442 / 3,125 | — |
| **合计** | ~61 MB | **~31.2 MB** | ~27.5 MB |

- **pck 基本压不动**：里面的 mp3、贴图、导入模型本身已经是压缩格式。按类别分：模型和场景 7.1 MB（35%），贴图 6.2 MB（31%），音频 4.2 MB（21%，三首背景乐约 3.4 MB），脚本 1.7 MB，字体 0.7 MB。
- **整个 pck 要先下完，引擎才启动**：Godot 网页版是这样设计的。大世界里才用到的怪物模型（灰狼 1 MB、虚空狐 0.76 MB、黑龙 0.73 MB……）也得在主城出现之前下完。
- **压缩**：GitHub Pages 只给 gzip，带 `Accept-Encoding: br` 请求也拿不到 brotli。换 brotli 只能省下 wasm 那 3.3 MB，约占总量 11%。
- **缓存**：
  - 响应头是 `cache-control: max-age=600` 加弱 ETag。CDN 回的 `age` 会占掉一部分有效期（实测 age 最高到 503），所以几分钟后再打开就要回源确认一次。确认走 304，每个文件约 0.4–0.7 s，代价很小。
  - **每次部署都换文件，所有人都得重下这 31 MB**。文件名不带内容哈希，没有 Service Worker 或 PWA 离线缓存。

### 2. 实测链路（只有本机这一台，两条出口）

| 链路 | 节点 | 首字节 | 吞吐 | wasm / pck 单独下载用时 |
|---|---|---|---|---|
| 本机代理 127.0.0.1:10808（浏览器和 curl 默认走这条） | Fastly 香港 HKG，CDN 命中 | 0.2–2.6 s（TLS 0.7–4.4 s） | 330–790 KB/s | wasm 13–26 s，pck 26–53 s |
| 本机直连（只在单条 curl 上加 `--noproxy`，没改代理设置） | Fastly 新加坡 QPG | 0.2–2.4 s（TLS 0.11 s） | 820–990 KB/s | wasm 10.3–12.4 s，pck 21 s |
| 对照：同一代理下载 Cloudflare 测速文件 20 MB | — | 1.4–2.0 s | 334–463 KB/s | 43–60 s |

**结论**：本机吞吐被出口链路卡在约 0.4–1 MB/s。测速文件同样慢，CDN 也都是命中，所以瓶颈在本机这条路，不在 GitHub Pages 源站。
浏览器里 wasm 和 pck 走同一条 HTTP/2 连接并行下载，合计约 0.8 MB/s，单连接带宽就是上限。

**这只代表本机这一个网络点**。其他人的耗时取决于各自到 Fastly 的线路，以下都没测到：中国大陆直连 github.io、手机 4G/5G、海外。
按 31.2 MB 的理论下限估算：1 MB/s（约 8 Mbps）约 31 s，2.5 MB/s（20 Mbps）约 12.5 s，6 MB/s（50 Mbps）约 5 s。长距离单连接通常跑不满带宽。

### 3. 浏览器里分段计时

测试条件：无界面 Edge，全新临时用户目录，ANGLE D3D11 驱动 GTX 1050 Ti，走本机代理。

| 阶段 | 第一次打开（空缓存） | 同一浏览器再开（有缓存） |
|---|---|---|
| 页面 + index.js | 0 → 3.9 s | 304 确认，约 0.7 s |
| **下载** wasm 10.25 MB | 3.9 → 26.9 s（22.9 s，437 KB/s） | 304，0.7 s |
| **下载** pck 20.89 MB（和 wasm 并行） | 3.9 → 42.8 s（38.9 s，525 KB/s） | 304，0.8 s |
| **解压** gzip | 浏览器边下边解，无法单独计时。本机 CPU 解 39.5 MB 约 0.12 s，可以忽略 | — |
| **编译** wasm（instantiateStreaming） | 5.4 → 26.9 s，**和下载完全重叠**，下载完即编译完 | 0.34 s（命中代码缓存） |
| 引擎启动（Godot 横幅，pck 进内存文件系统） | 43.1 s | 4.9 s |
| **初始化** 渲染器（基础着色器编译） | 43.1 → 53.9 s（10.8 s） | 0.9 s |
| **初始化** 主城场景和音频采样 | 53.9 → 约 93 s（约 39 s） | 约 10 s |
| **初始化** 游戏预热 `[warm] hall` | 约 93 → 171.1 s（**78.1 s**：着色器 10.8、藏着的部件 41.5、特效 12.9、文字 11.5） | 10.2 s |
| **可以玩** | **171 s** | **25 s** |

**结论**：
- 第一次打开共 171 s，其中网络下载约 39 s（约 23%），**引擎和游戏初始化约 128 s（约 75%）**。初始化里大头是着色器、材质、特效的首次编译：在 Windows 的 ANGLE D3D11 上要走 HLSL 编译，首次很慢。浏览器会把编译结果缓存在本地，所以再开只要 10 s 左右。
- 用户感觉到的「下载很慢」，实际是「下载进度条约 40 s + 之后黑屏或载入字样约 2 分钟」两段加在一起。
- 网速快的用户下载段能缩到几秒，但**首次初始化这 2 分钟不会因为网速变快而变短**。
- 注意事项：
  - 无界面浏览器的数字可能比有界面的偏慢。
  - 测量时机器上还有其他会话的 Godot 进程，有 CPU 争用。
  - 本地离线测过的首启预热是 51–58 s，同一量级。
  - 真实手机 GPU（Adreno、Mali、苹果 Metal 等）的编译耗时完全没测。

顺带看到：进入主城时控制台有一条未捕获的 Pointer Lock 报错，需要用户先点一下页面才能锁鼠标。无界面、无点击的情况下必然出现，不影响加载，本次没往下查。

## 二、线上包是否支持多人联机

| 层面 | 结论 | 依据 |
|---|---|---|
| 代码里有没有联机 | **有，但只是局域网方案** | `net.gd`：ENet（UDP 24680）建房和加入；局域网 UDP 广播 255.255.255.255:24681 发现房间；最多 40 人。入口是主城择境门 → 关卡卡片 → 入境页选人数（独行 / 双人 / 四人）→「开始匹配」。界面上没有输入 IP 或建房的入口，`host` / `join` / `join_ip` 只给自检脚本用（`level_select.gd:24`）。 |
| 线上网页包能不能联机 | **不能，线上网页版没有任何真人联机** | `main.gd:883` 的 `_matchmake` 判断 `OS.has_feature("web")` 后直接单人进入，选双人或四人时缺的队友全由 AI 道友补位，载入时也不提示「这是 AI」。线上 pck 解包核对：102 个脚本里只有 `net.gdc` 用到 ENetMultiplayerPeer 和 PacketPeerUDP，没有任何 WebSocket、WebRTC 或 HTTP 客户端代码，出现的 IP 字串只有 127.0.0.1 和 255.255.255.255；`main.gdc` 里有 `has_feature`、"web"、`_matchmake` 和对应的载入提示文字，和源码一致。引擎 wasm 自带 WebSocket 和 WebRTC 类，但游戏没用。 |
| 需要的服务能不能连上 | **没有服务**：没有部署任何匹配、中继或信令服务器 | GitHub Pages 是纯静态托管，不能跑 WebSocket 服务；脚本里也没有外部网址。 |
| 跨网络 / 手机浏览器的限制 | 浏览器（含手机）不能开原始 UDP/TCP 端口，也收不到局域网广播，**现在的 ENet + 广播方案在任何浏览器里都用不了**。网页要联机得改成 WebSocket（要自己架服务器）或 WebRTC（要信令服务器，加 STUN/TURN 穿透）。手机浏览器切到后台还会挂起页面、断开连接。 | 这是设计决策，本次只记录、不做。 |
| 桌面原生版 | 只能在同一局域网的广播范围内互相发现，没有公网 IP 输入、NAT 穿透或中继，**跨网络不行**；Windows 防火墙还要放行 UDP 24680 和 24681。另外**项目只有 Web 一个导出预设，没有发布过原生桌面包**。 | `export_presets.cfg` 只有 `[preset.0] Web` |
| 有没有做过两台设备真实联机 | **从来没做过**。以往联机自检都是同一台机器开多个进程，走 127.0.0.1（本专项 QA 报告第 241 行；AI 道友双开 `--net=ally_host/ally_mate`）。本次也没测。线上网页版没有联机，也就无从测起。 | — |
| 本次没做的 | 没在线上实际点击走一遍「开始匹配」：发行版网页模板不接收测试参数。线上「网页版直接单人 + AI 补位」这一结论来自线上脚本解包加同一份源码的分支，不是点击实测。 | — |
